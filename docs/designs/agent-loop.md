# Design: The agent loop (plan in, check out)

## Problem Statement

xD's CLI is mostly for agents and MCP servers making procedural edits to an
organizational system. ADR 0002 designs plan and apply (operations as data,
check, journaled apply, undo through jj), but none of it exists in code yet:
`xd-core` has addresses, schemes and the registry, and there is no plan type,
no check, no apply, no journal and no CLI crate. Until that loop exists, an
agent can't safely change a system, and the showcase command can't run.

The showcase is `xd spark-joy`: run it in a messy folder (a Desktop, a
Documents folder) and watch every file and folder get organized into a
Johnny.Decimal system, with progress lines:

```
Walking all subdirectories to gather files and create the "aLDex" (Antilibrary Index) ...
Creating flat aLDex ... Done.
Embedding file contents ... Complete.
Finding clusters ... Done.
Designating Areas ... Done.
Assigning Categories ... Done.
Mapping Items ... Done.
Moving to new AC.ID Path ... Done.
Complete.
```

`xd spark-joy` is fully automatic; `xd spark agent` is the interactive
version. Which first impression is strongest (step by step, full auto, or
"ta-da, here's the plan") is to be settled by A/B testing.

## What Makes This Cool

- **xD is the guardrail that makes it safe to let an agent loose on your
  files.** The agent can be as creative as it likes; xD turns its proposal
  into a plan, checks it against the formal invariants, applies it with a
  journal, and can undo all of it.
- **Johnny.Decimal's limits are a clustering spec.** At most 10 areas, 10
  categories per area and 99 IDs per category: "organize this mess" is
  hierarchical clustering with branching capped at 10.
- **Fearless undo.** `xd undo` puts the Desktop back exactly as it was, so
  people will run it on a folder they're scared of.

## Constraints

- AGENTS.md: keep the core pure (no file system access outside apply and
  tests' temp dirs); no trait or plugin interface before a second
  implementation; a design change gets an ADR.
- Defaults follow the Johnny.Decimal spec, not the `jd` CLI.
- The CLI is used by agents first: non-interactive, JSON in and out,
  deterministic output.

## Premises

Agreed in the session:

1. The CLI's main users are agents and MCP servers. Every command is
   non-interactive by default, takes and emits JSON, and is deterministic.
2. xD never decides how to organize. It reports what's there (scan → aLDex)
   and checks and applies what an agent or a person proposes. Clustering and
   naming happen outside the core.
3. Every change goes through a plan: propose → check against the invariants →
   apply (journaled) → undo through jj, for agents, people and spark-joy alike.
4. spark-joy is a thin recipe over the same commands (scan, propose, plan,
   apply), not a special code path. Its modes (auto, agent/interactive,
   ta-da) differ only in how the plan is shown and approved.
5. Build the agent-facing loop on a local folder first: scan → plan → check
   → apply → undo. spark-joy, remote backends and shared systems come after.
6. The aLDex is a new artifact; its format needs an ADR, and it should become
   the new system's `00.00` JDex once applied.

## Approaches Considered

### Approach A: Plan in, check out (chosen)
Agents submit an operation list as JSON; xD checks it, applies it with a
journal, and can undo it. `xd scan` emits the aLDex. Effort M (human ~2 weeks
/ CC ~1-2 days), risk low.

### Approach B: Full declarative loop + MCP server
All of ADR 0002's three-way reconciliation plus an `xd-mcp` crate. Rejected
for now: the riskiest piece comes first and there's no demo for weeks.

### Approach C: Sandbox first
Agents iterate against the `simulate` interpreter and commit when happy.
Deferred: it still needs A's apply and journal; it's the natural next layer
for the "ta-da" mode.

## Recommended Approach

Approach A. It builds what B and C both depend on (the operations, check,
apply, journal and invert from ADR 0002) and is the shortest route to an
agent organizing a real folder and safely undoing it.

Accepted shortcut (decision `99191eb3`): no three-way reconciliation, so
edits made by hand on disk aren't detected and the config can lag the disk
until `RecordInConfig` operations are emitted reliably. Upgrade when a second
writer (hand edits or a teammate) touches a system, or when spark-joy needs
desired-state input.

### Shape of v1

Commands (all JSON on stdout, errors as JSON with a finding code, nonzero
exit on failure):

| Command | Does |
|---|---|
| `xd init <dir>` | Makes `<dir>` a system: writes the config, creates `00-09 System` holding the config, the `00.00` JDex and a jj repository rooted there (so jj only ever tracks the config and JDex, never the files being organized), plus a `.xd/` state folder. Explicit, separate from any plan, and not reversed by `xd undo`. Every other command refuses a folder that isn't a system. |
| `xd scan <dir>` | Walks the folder read-only and emits the aLDex: one record per file and folder (path, kind, size, mtime, content hash). No numbering. Excludes `.xd/` and `00-09 System`. |
| `xd check <plan.json> [-C <dir>]` | Finds the system from `-C` or by walking up from the current directory to `.xd/`, loads its state, re-scans the system itself to get a current aLDex (in `xd-cli`, before calling the pure check; never a stored or caller-supplied scan) and runs the check interpreter (see Check below). Emits findings and, if there are none, a receipt: the plan's content hash. |
| `xd apply <plan.json> --receipt <hash>` | Refuses unless the receipt matches the plan's hash; the receipt only binds the plan the agent saw to the plan applied, it doesn't prove check ran. Apply then re-runs check against the system's *current* state and a fresh re-scan, the same way `xd check` does, (another apply may have taken a number since) and runs only a `Plan<Checked>`, keeping ADR 0002's typestate. Then it applies each operation through the local directory backend, journaling each step before it runs, and commits the config and JDex changes in the jj repository inside `00-09 System`. |
| `xd undo` | Inverts the last applied plan and applies it like any plan (check and preconditions included), reversing folder changes only through xD's inverses; jj's history only restores the config and JDex. The inverted plan is recorded as an undo that marks its source plan undone, not as a new undoable plan. v1 depth: one step back per call, walking back through the stored plans; undoing an undo is not a redo. |
| `xd recover` | After a crash mid-apply, rolls back the completed steps recorded in the journal. |

**Operations.** v1 takes `CreateFolder`, `RemoveEmptyFolder`, `Rename`,
`Move`, `WriteJdexEntry` and `RecordInConfig` from ADR 0002's examples, and
adds one path-based operation, because loose files on a Desktop have no
address and `Move` only renumbers addressed entries:

| Operation | Inverse |
|---|---|
| `Adopt { from_path, to_address, name, size, mtime, hash }` | `Release { from_address, name, to_path }` |

`Adopt` moves an unaddressed file or folder (as one unit) into an ID folder.
It carries the size, mtime and hash from the scan as its precondition. The
enum is `#[non_exhaustive]`. Plan, operations, check and invert live in
`xd-core` (pure); `init`, apply and the directory backend live in a new
`xd-cli` crate, the only place that touches the disk.

**What a file becomes.** A file or folder is placed *inside* an ID folder; it
is not an ID itself. IDs are created by `CreateFolder` in the plan and files
are adopted into them. Existing folders are adopted whole, not flattened,
unless the plan adopts their contents one by one.

**Check** is a pure function in `xd-core`: `check(plan, state, aldex) -> findings`, where `state` is the system's config (`Live` and `Retired`) and JDex entries, and `aldex` is the scan, which already records each symlink with its target. It decides everything from that data and touches no disk. It rejects with a distinct finding code:

| Finding | When |
|---|---|
| `reused-number` | a number in `Retired` is used again |
| `duplicate-number` | two entries share a number |
| `not-closed` | an ID's category or area doesn't exist |
| `outside-root` | a write resolves outside the system root, including through a symlink target recorded in the aLDex |
| `capacity` | the plan exceeds the scheme (with standard zeros on: 9 usable areas `10-19`…`90-99`, since `00-09` is the system's own; 9 usable categories per area, `a1`…`a9`, since `a0` is the area's own; IDs `.11`–`.99`, 89 per category, with `.10` reserved per jd-formal 2.1) |
| `no-inverse` | an operation has no inverse and isn't marked irreversible |

**Apply** checks preconditions per operation before running it and fails
with a finding instead of overwriting:

| Finding | When |
|---|---|
| `stale` | the source's size, mtime or hash differs from the scan |
| `collision` | the destination already exists |
| `missing` | the source no longer exists |

On any failure, apply rolls back the completed steps in reverse (ADR 0002
decision 5.2) and exits nonzero.

**Where state lives.** `.xd/journal/<plan-id>.jsonl` holds one line per step,
written before the step runs and marked done after. `.xd/plans/<plan-id>.json`
stores every applied plan; `xd undo` reads the newest one not yet undone, and
the jj bookmark from ADR 0002 marks it. If a command finds a journal with an
unfinished step, it refuses to run and points to `xd recover`, which rolls back
rather than resumes.

**Scan edge cases.** Symlinks are recorded as links (target included) and
never followed; adopting one whose target is outside the root fails `check`
with `outside-root`. Unreadable files are recorded with an `error` field and
no hash, so they can't be adopted (no precondition). Hidden and system files
(`.DS_Store`, `desktop.ini`, dotfiles) are recorded with `hidden: true`; the
spark-joy recipe leaves them in place.

spark-joy v0 is then an agent recipe, not xD code: `xd init` → `xd scan` →
agent embeds, clusters into ≤9 areas / ≤9 categories per area / ≤89 IDs per category, names
them, emits a plan → `xd check` → `xd apply`. Files that don't cluster go to
each category's `.01` Inbox. If the folder holds more items than the scheme
fits, the recipe groups files into shared IDs; check's `capacity` finding is
the backstop.

## Open Questions

- aLDex format: JSON Lines or one JSON document? What fields beyond path,
  size, mtime and hash? (Needs its own ADR, per premise 6.)
- How does `xd scan` treat files inside the folder that are already JD
  addressed (parse maps them to an address, not `skip`)?
- Duplicates (same content hash): does xD report them in the aLDex, or is
  that left to the agent?
- `workflow-rules.md` predates ADR 0002 and the `xd` naming; link it as
  background or remove it.

## Success Criteria

- An agent (Claude Code, through the shell) runs `xd scan` on a real messy
  folder, writes a plan, and `xd apply` organizes it into a JD system.
- `xd undo` then restores the folder: the set of (path, hash) pairs from a
  fresh `xd scan` equals the set from the scan before apply. `xd init`'s
  metadata (`.xd/` and `00-09 System`, which holds the jj repository) is excluded from scans and stays
  after undo.
- `xd check` rejects a hand-crafted bad plan for each invariant with a
  distinct finding code, covered by tests in `crates/xd-conformance` and
  named regressions where bugs are found.
- The CI checks in AGENTS.md pass.

7. Then Approach C's `simulate` for the "ta-da" preview, and the A/B test of

**Problem**

> Check is now `check(plan, state, aldex)`, but neither `xd check` nor apply's re-check says where the aldex comes from. `xd check` takes only the plan and `-C`; 'loads its state' covers config and JDex, and nothing stores a scan in `.xd/` (scan only prints to stdout). ### Review sections

**1. Architecture.**
Design-twice (new `plan` module and `xd-cli` crate): Shape 1 (plan) = `plan::check(plan, &Registry, &Scheme, &Aldex) -> Vec<Finding>` clones the Registry and simulates. Shape 2 = `Registry::simulate(&Plan) -> Result<Registry, Vec<RegistryError>>`, with path rules in xd-cli. Pick Shape 1: one interface hides number rules (via Registry), path rules (outside-root, Adopt) and inverse rules behind one call; Shape 2 puts path knowledge in xd-cli and gives check two entry points (red flag 6).
Red flags: (5) split ownership: "newest not yet undone" is recorded in both `.xd/plans/` and the ADR 0002 jj bookmark (agent-loop.md "Where state lives"); D20. Others: none found; RegistryError→finding mapping is one exhaustive `match` (no hand-synced list).
